# Agent Skills Updater

Сервер поддерживает готовые папки `skills/<name>/` в
[agent-skills](https://gitea.example.org/dim/agent-skills).
Клиенты синхронизируют только этот Git-каталог и подключают его папки
ссылками в `.agents/skills` и `.claude/skills`. Внешние Git/HTTPS-источники,
выбор версий и SHA256 обслуживаются исключительно сервером.

`client/` содержит эталон установщиков Linux/Windows. `server/` содержит
управление каталогами из `server/catalogs.json`. Файлы скиллов хранятся в
обслуживаемых каталогах, не в репозитории updater.

## Как устроена синхронизация

Сервер при регистрации сразу скачивает и проверяет весь скилл и публикует
`skills/<name>/` вместе с записью в `sources.json`. При обслуживании старого
каталога без файлов он заполняет все отсутствующие папки именно закреплёнными
версиями. Переход не одобряет новые внешние версии.

Клиент ежечасно коммитит правки только зарегистрированных `skills/<name>/`,
получает изменения из origin, объединяет совместимые коммиты,
отправляет результат и создаёт ссылки на эти папки. Редактирование
установленного скилла сразу меняет его файлы в Git-копии. Клиент не скачивает исходники, не проверяет
внешние ветки, не ведёт кеш версий и не редактирует реестр.
Параметры и установка: [client/README.md](client/README.md).

На сервере `sources.json` хранит исходный `source`, закреплённую `revision`,
`content_sha256`, `executable_sha256` и флаг `auto_update`. При следующем
обслуживании сервер сравнивает содержимое папок с реестром и распознаёт доработки, пришедшие
клиентскими Git-коммитами. Для внешнего скилла появляется `customization`
с текущим хешем и исходной базой; для собственного скилла обновляются
revision и хеш. До этого файлы уже распространяются между клиентами через Git.

## Внешние источники и обновления

Работайте на i3 из `/home/dim/Dev/agent-skills-updater`. Нужны Python 3.9+,
Git, Bash, flock и пользовательский systemd. Каталоги — отдельные Git-копии
с реестром версии 2, настроенными origin/upstream и доступом без запроса
пароля. Пути в `server/catalogs.json` относительны к этому файлу.

```bash
python3 server/manage.py status
python3 server/manage.py maintain --dry-run
python3 server/manage.py maintain --apply-auto --publish
```

Для одного каталога добавьте `--catalog agent-skills` перед подкомандой.
`status` проверяет локальную конфигурацию и клиентские файлы. `--dry-run`
не делает pull и не меняет каталог, но может пополнить серверный кеш и отчёт.
`maintain` без `--apply-auto` материализует закреплённые скиллы и учитывает
общие доработки, оставляя внешние обновления на просмотр.

Регистрация Git-источника:

```bash
python3 server/manage.py --catalog agent-skills register example-skill --git-url https://example.org/owner/repo.git --path skills/example-skill --ref refs/heads/main --auto-update yes --publish
```

Для одиночного `SKILL.md` используйте `--url https://.../SKILL.md` вместо
Git-параметров. Содержимое должно иметь frontmatter с совпадающим именем
и description. Сервер проверяет структуру и точный SHA256, включая бинарные
файлы и CRLF. Проверка не исполняет команды из скилла и не оценивает смысл
инструкций. Внутренние ссылки и Git-метаданные скиллов не поддерживаются.

```bash
python3 server/manage.py --catalog agent-skills check
python3 server/manage.py --catalog agent-skills approve example-skill --revision <revision-из-отчёта> --publish
```

`check` показывает обновления и обнаруженные доработки, сохраняя файлы
и реестр. Одобрение проверяет точную revision на момент выполнения.
`auto_update=false` оставляет внешнюю версию до явного одобрения. Изменения
вне папки скилла не меняют его закрепление.

## Собственные скиллы

Подготовьте папку с `SKILL.md`, скриптами и справочными файлами:

```bash
python3 server/manage.py --catalog agent-skills register-local my-skill --directory /path/to/my-skill --publish
```

Команда импортирует папку в `skills/my-skill/` и публикует её вместе с
реестром. Можно указать уже скопированную туда новую папку; допускаются
только её неотслеживаемые файлы, остальные локальные изменения сохраняются
до ручного решения. Имя в frontmatter должно совпадать с `my-skill`.

Запись `source: {kind: "local", path: "skills/my-skill"}` не имеет внешнего
URL. `auto_update=false`, revision и content_sha256 равны хешу содержимого.
Сервер показывает статус `local` и обновляет этот хеш при изменении файлов.
Клиенты работают с такой папкой точно так же, как с внешним скиллом.

## Конфликты

Если общая папка доработана, любое изменение внешнего скилла даёт
`upstream-conflict`. Сервер сохраняет вашу папку и исходное закрепление,
пишет отчёт в `.git/skill-updates.json` и возвращает ненулевой код.
`auto_update` и `approve` не обходят конфликт. Остальные скиллы продолжают
обслуживаться. Отсутствие скилла/ветки в источнике или ошибка загрузки
не является командой удаления установленной папки.

В отчёте указаны базовая revision/хеш, ваша папка и найденная входящая
версия. Сервер хранит проверенные внешние версии в своём кеше
`~/.cache/agent-skills/upstream-versions/` (или `$XDG_CACHE_HOME`).
Сравнение учитывает байты и Git executable bit. Старые записи без
executable_sha256 дополняются по закреплённой версии; SHA256 содержимого
сохраняет прежний формат. Ключ серверного кеша учитывает оба хеша.
Git-базу можно восстановить по закреплённой revision; изменяемый HTTPS URL
может больше не отдавать старую версию. Сравнение подходов:
[исследование](research/local-skill-conflicts.md).

```bash
python3 server/manage.py --catalog agent-skills resolve example-skill --revision <incoming-revision> --shared-hash <shared-SHA256> --strategy keep-shared --publish
python3 server/manage.py --catalog agent-skills resolve example-skill --revision <incoming-revision> --shared-hash <shared-SHA256> --strategy take-upstream --publish
```

`keep-shared` оставляет всю вашу папку и принимает входящую версию как базу
следующих проверок, без слияния её файлов. `take-upstream` заменяет содержимое
той же папки входящей версией. История обеих сторон сохраняется в Git.
Для ручного объединения отредактируйте и опубликуйте файлы, затем используйте
`keep-shared` с их текущим хешем. Обе команды останавливаются, если revision
или общая папка изменились после просмотра.

Независимые коммиты станций клиент объединяет обычным Git merge во временной
рабочей копии, сохраняя историю обеих сторон. Только успешный результат
подключается к основной копии через fast-forward. При настоящем конфликте
установленные файлы остаются без маркеров слияния, локальный коммит сохраняется
для ручного разбора. Reset, clean, force-push и rebase не используются. Ручные коммиты, staged-файлы и изменения
вне зарегистрированных папок автоматически не отправляются. Клиент соблюдает
Git ignore и добавляет только проверенные пути из статуса. Сервер отдельно
публикует проверенные файлы внешнего источника: уже отслеживаемые upstream
файлы сохраняются даже при совпадении с его .gitignore. Локальные игнорируемые
файлы не входят в хеш доработки и не публикуются.

Если источник удалён или недоступен, свою версию можно сохранить как
собственный скилл без обращения к источнику:

```bash
python3 server/manage.py --catalog agent-skills resolve example-skill --shared-hash <shared-SHA256> --strategy detach --publish
```

`detach` проверяет текущий хеш файлов, меняет source на local и отключает
внешние обновления. Папка и Git-история остаются на месте.

Перед заменой папки сервер повторно проверяет её байты и права исполнения.
Если во время скачивания появились правки, обновление останавливается.
Предыдущая папка сохраняется в `.git/skill-backups/<name>-<id>/content`,
включая файлы, которые редактор продолжает держать открытыми. Путь выводится
в журнал; резервные папки автоматически не очищаются. Игнорируемые локальные
файлы переносятся в новую папку, а пересечение с входящим файлом останавливает
обновление с сохранением исходной папки.

## Обслуживание и переход со старой установки

```bash
python3 server/manage.py --catalog agent-skills deploy-client --publish
bash server/install.sh
systemctl --user start agent-skills-updater.service
journalctl --user -u agent-skills-updater.service -n 30
```

`deploy-client` обновляет клиентские файлы и заполняет отсутствующие папки
закреплёнными скиллами. `.agent-skills-client.json` хранит владение шаблонами:
ручные изменения развёрнутых клиентских скриптов вызывают конфликт и сохраняются.
Правьте эталоны только в `client/`. Новые файлы должны попасть в CLIENT_FILES
и миграцию манифеста. LF/CRLF не создают ложных изменений шаблонов.

Старые `customizations/<name>/<hash>/` переносятся в `skills/<name>/` при
обслуживании. Проверенные старые папки убираются из рабочей копии, сохраняясь
в Git. Неизвестные изменения и чужие папки останавливают миграцию.

При первом запуске новый клиент переводит принадлежащие ему ссылки из
`versions/<name>/<hash>` на `skills/<name>/`. Неизменённые кеши переключаются;
локальные доработки импортируются в Git, если базовая версия совпадает.
При несовпадении обе копии сохраняются для ручного разбора. Старые кеши
не удаляются. Хеширование в клиенте оставлено только для этого перехода.

Ежедневная служба обновляет чистую копию updater и выполняет
`maintain --apply-auto --publish`. Для работы после выхода нужен linger.
Отключение: `bash server/install.sh --uninstall`. Клиентские расписания —
ежечасные systemd/Windows-задачи; планировщик T3 для них не нужен.

Сервер и клиент блокируют одну Git-копию на время операции. Ошибка одного
каталога не мешает остальным. Неудачный push автоматического коммита
повторяется при следующем запуске, если история позволяет. Грязные рабочие
копии и неопубликованные ручные коммиты сохраняются.

Управляющие скиллы находятся в `server/skills/`, указатели Codex —
в `.codex/skills/`. Тесты: `python3 -m unittest discover -s tests -v`.
`AGENT_SKILLS_PWSH=/path/to/pwsh` включает PowerShell-проверки в Linux;
они не заменяют проверку Windows-junctions и Планировщика на реальной Windows.
