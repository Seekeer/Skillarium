# Распространение Skillarium: движок, сервер, клиенты, обновления

Статус: план по решениям беседы от 2026-11-05. macOS не поддерживается.

## Цель

Любой человек ставит Skillarium одной командой на свой сервер (у нас — i3),
получает свою библиотеку скиллов в Gitea и команды подключения клиентов
Windows/Linux. Система и приложение обновляются сами, без форков и слияний с
чужим репо. Свои скиллы человек добавляет в свою библиотеку как сейчас.

## Принятые решения

1. **Движок и библиотека разделены.**
   - Движок Skillarium — публичный репо на GitHub: клиент, `projects.*`,
     `server/`, приложение, системные скиллы, установщики.
   - Библиотека — репо пользователя в его Gitea: `skills/`, `sources.json`,
     `agent-skills.json`, `upstream/`, workflow проверки. Кода движка в
     библиотеке нет.
2. **Один путь доставки движка — выпуск Skillarium.**
   - Приложение содержит движок своей же версии.
   - Машины без UI (сервер) ставят тот же движок архивом и обновляются
     командой `skillarium self-update`.
   - Версии движка и приложения не расходятся.
3. **Установка движка на машине:**
   - `versions/<v>/` + `current` (symlink в Linux, junction в Windows);
   - путь: Linux `~/.local/share/skillarium`, Windows
     `%LOCALAPPDATA%\Skillarium`;
   - расписания всегда вызывают `current/...`;
   - хранятся 2 предыдущие версии, `skillarium rollback`.
4. **Совместимость машин одной библиотеки задаётся форматом.**
   - `agent-skills.json` получает `format` (целое).
   - Движок, видящий формат новее своего, переходит в режим только чтения:
     скиллы работают, публикаций нет, сообщение «обновите Skillarium».
   - Формат поднимает только назначенный сервер PR с миграцией.
5. **Роли не меняются.**
   - i3 — назначенный сервер: внешние источники, реестр, миграции.
   - Gitea — `main`, PR, проверка `policy.py`, автослияние.
   - Клиенты — правки, синхронизация, разбор конфликтов в приложении.
6. **Клиенту нужен только адрес библиотеки.** Остальное (сервер, хостинг,
   формат) он читает из самой библиотеки.
7. **Токены никогда не попадают в печатаемые команды.** Они вводятся
   интерактивно и хранятся в Git credential helper.

## Целевая структура

```
skillarium (GitHub)                     agent-skills (Gitea, библиотека)
  engine/                                 skills/<name>/
    install.sh, install.ps1               sources.json
    scripts/ (client, bindings, vbs)      agent-skills.json  {format, server, policy_engine}
    projects.sh, projects.ps1             upstream/<name>/
    server/ (manage, policy, hosting…)    .gitea/workflows/policy.yml
    skills/ (системные скиллы)            README.md (команды подключения)
    templates/library/
  app/ (Electron)
  tests/
  .github/workflows/ (tests, release)
```

## Этапы

Порядок: 1 → 2 → (3 ∥ 6) → (4 ∥ 5) → 7 → 8.

### Этап 1. Движок перестаёт жить внутри библиотеки (в текущем репо)

Подготовка без смены репо, все тесты зелёные на каждом шаге.

1. **Клиент и `projects.*` получают путь к библиотеке явно**, а не как
   «папку, где лежит скрипт».
   - Источник пути: `--library <path>` / `-Library`, переменная
     `SKILLARIUM_LIBRARY`, иначе конфиг `config.json`.
   - Сейчас путь вычисляется из `dirname` скрипта.
2. **Серверные команды** (`server/manage.py`, `run.sh`, `install.sh`)
   принимают `--repo` так же.
3. **Приложение** (`app/main/backend.cjs`) вызывает `projects.*` из каталога
   движка и передаёт библиотеку параметром. Сейчас скрипт берётся из
   `path.join(library, script)`.
4. **Формат библиотеки:**
   - поле `format` в `agent-skills.json`;
   - проверка в клиенте, сервере и `policy.py`;
   - режим только чтения;
   - команда `manage.py migrate` с реестром миграций (первая миграция
     добавляет `format: 1`).
5. **Задачи по расписанию** (systemd-юниты, Планировщик) вызывают движок по
   абсолютному пути движка, библиотека передаётся параметром.

Готово, когда тесты проходят с движком и библиотекой в разных каталогах
(фикстура разносит их).

**Статус (ветка `skillarium/engine-split`).**

- Сделаны пункты 1–3 и 5: `scripts/locate.*`, `--library`/`-Library`,
  `--repo` для сервера, `SKILLARIUM_LIBRARY`, конфиг Skillarium.
- Из пункта 4 сделаны поле `format`, его проверка в клиентах и на сервере,
  режим только чтения и предупреждение в приложении.
- Не сделана команда `manage.py migrate`. Её стоит добавить вместе с первой
  настоящей миграцией, пока реестр миграций пуст.
- Тесты: `tests/test_engine_layout.py`. Основная фикстура `tests/fixture.py`
  по-прежнему копирует движок в библиотеку (старая раскладка); разнести её
  стоит на этапе 7, когда старая раскладка уйдёт.
- После ревью формат проверяется во всех путях записи: публикация,
  одобрение и разрешение предложений, разрешение конфликта.

### Этап 2. Репо движка на GitHub и выпуски

1. **Создать `skillarium` на GitHub** и перенести файлы движка с историей
   (`git filter-repo --path ...`). Перенести тесты; `fake_hosting.py` остаётся
   имитацией Gitea.
2. **CI на GitHub Actions:**
   - Linux-тесты;
   - нативные Windows-тесты на `windows-latest`: junction, Планировщик,
     PowerShell 5.1. Отдельный Windows-раннер больше не нужен.
3. **Выпуск по тегу `v*`:**
   - `skillarium-engine-<v>.tar.gz` и `.zip`;
   - установщик приложения: NSIS для Windows, AppImage для Linux;
   - `latest.yml` (для electron-updater) и `latest.json` (для
     `self-update`: версия, файлы, sha512, минимальный и максимальный
     `format`);
   - `install.sh` и `install.ps1` как отдельные файлы выпуска, по адресу
     `releases/latest/download/...`.
4. **Каналы `stable` и `beta`:** pre-release на GitHub — это beta.

Готово, когда тег даёт полный набор файлов выпуска, а ссылки
`latest/download` работают.

**Статус (локальный репо `Skillarium`, ещё не опубликован).**

- Сделано: история движка без библиотеки, шаблон `templates/library/`
  (с `policy_engine` — версия и sha512 выпуска, чью политику запускает
  проверка PR), CI на GitHub Actions, выпуск по тегу после полного прогона
  тестов: архивы движка, `.sha512`, `latest.json` с `format: {min, max}`.
- Перенесено: установщики приложения и `latest.yml` — на этап 6;
  загрузочные `install.sh`/`install.ps1` как файлы выпуска — на этапы 3 и 5,
  когда появятся установщики движка.
- Beta: `releases/latest/download` на GitHub всегда указывает на stable,
  поэтому `self-update --channel beta` (этап 3) выбирает выпуск через
  GitHub API releases, а не по адресу `latest`.

### Этап 3. Установка движка и самообновление

1. **`install.sh engine` / `install.ps1 -Mode Engine`:**
   - скачивает архив, проверяет sha512;
   - раскладывает его в `versions/<v>`, переключает `current`;
   - кладёт команду `skillarium` (`~/.local/bin`, на Windows — `.cmd` в PATH
     пользователя).
2. **`skillarium self-update [--channel beta]`:**
   - читает `latest.json`;
   - пропускает версию, если её `format` ниже формата библиотеки;
   - скачивает, переключает `current` одним действием, удаляет старые
     версии сверх двух.
   - Запускается ежечасным таймером. На машине с приложением его не
     вызывают: там обновляет приложение.
3. **`skillarium rollback`.**
4. **`skillarium status`:** версия движка, формат библиотеки, режим
   (норма или только чтение), канал.

Готово, когда тесты с локальным HTTP-сервером выпусков проходят: обновление,
битый хеш, откат, прерванная загрузка, запуск таймера во время переключения.

### Этап 4. Установка сервера: `install.sh server --repo <url>`

Одна команда на i3. Повторный запуск — «починить или обновить».

1. **Проверка зависимостей:** Git, Python 3.9+, jq, curl, flock, systemd
   `--user`, linger. Для недостающего печатается команда установки.
2. **Установка движка** (этап 3).
3. **Токен Gitea** — интерактивно или `--token-file`, сохраняется в
   credential helper. Опция `--bot <user>` создаёт служебного пользователя с
   токеном для машин.
4. **Библиотека:**
   - репо нет — создать;
   - репо пустое — инициализировать из `templates/library` (`format`,
     `server.machine` = имя машины, пустые `sources.json`/`skills/`,
     workflow, README);
   - репо уже библиотека — подключиться и переназначить сервер через
     `manage.py assign-server`.
5. **Настройки Gitea через API:**
   - Actions включены;
   - защита `main` с обязательной проверкой `policy`;
   - автослияние разрешено.
   - Наличие раннера проверяется. `--runner` регистрирует act_runner на этой
     же машине.
6. **Проверка PR в библиотеке.**
   - Workflow скачивает `policy.py` версии `policy_engine` из основной ветки
     и проверяет sha512.
   - Сервер поднимает `policy_engine` своим PR после собственного
     обновления.
   - Требование: раннер имеет доступ к GitHub.
7. **Таймеры:** обслуживание (ежедневно), `self-update` (ежечасно).
   Синхронизация клиента — только с `--with-client`. Старые юниты
   `agent-skills-server.*` переводятся по маркеру, как сейчас.
8. **Вывод** готовых команд подключения клиентов Windows и Linux; они же
   записываются в README библиотеки.

Готово, когда тесты на `fake_hosting.py` (дополнить: создание репо, защита
веток, настройки Actions) проходят для всех трёх случаев репо, а повторный
запуск ничего не дублирует.

### Этап 5. Установка клиента: `install.ps1 -Library <url>` / `install.sh client --library <url>`

1. **Скачивание приложения** с GitHub Releases и тихая установка в профиль
   пользователя:
   - Windows: NSIS `/S`, per-user;
   - Linux: AppImage в `~/.local/bin` + `.desktop`.
   - `--no-app` ставит только движок (Linux без графики).
2. **Конфиг** `config.json` с полем `library`: `%APPDATA%\Skillarium` или
   `~/.config/skillarium`.
3. **Токен пользователя Gitea** → credential helper; проверка права записи
   через API.
4. **Клон библиотеки** в каталог по умолчанию (`~/Skillarium/library`,
   переопределяется `-Path`). Если клон уже есть, он принимается, а не
   создаётся заново.
5. **Ссылки скиллов, расписание синхронизации, запуск приложения.**

Готово, когда установка во временный HOME проходит с имитацией выпусков и
Gitea, а на Windows — нативно в CI.

### Этап 6. Приложение

1. **electron-builder:**
   - иконки из `assets/brand`;
   - NSIS per-user, AppImage;
   - движок кладётся в `resources/engine`.
2. **electron-updater** с провайдером GitHub; каналы stable/beta;
   «перезапустить для обновления».
3. **При старте и после обновления** приложение раскладывает свой движок в
   `versions/<v>` и переключает `current`. Версия движка всегда равна версии
   приложения.
4. **Первый запуск без конфига:** экран «Подключить библиотеку» (URL, токен,
   папка) — те же шаги, что в этапе 5.
5. **Баннер «только чтение»**, когда формат библиотеки новее; кнопка
   обновления.
6. *Позже:* список предложений внешних обновлений
   (`agent-skills/update/...`) рядом с разбором конфликтов.

Готово, когда Playwright-тесты покрывают первый запуск, режим только чтения
и работу с движком из `current`.

### Этап 7. Перевод текущей установки

1. **Мостовой выпуск в старой библиотеке.** Последняя версия встроенного
   `client.sh`/`client.ps1` при синхронизации:
   - ставит движок Skillarium (без приложения);
   - пишет конфиг с текущим клоном;
   - переводит своё расписание на `current/...`.
   Без этого удаление файлов движка из библиотеки оборвёт синхронизацию на
   машинах.
2. **Подождать**, пока все машины отчитаются через `status`: на сервере
   видны их последние синхронизации.
3. **Админский PR, удаляющий из `dim/agent-skills` файлы движка.**
   Предварительно правило `policy.py` разрешает это одному явному PR.
4. **На i3:** `install.sh server --repo .../dim/agent-skills` (режим
   подключения к существующей библиотеке).
5. **На клиентах:** поставить приложение (команда из README библиотеки).
   Клон и расписание уже переведены мостом.

Готово, когда все машины синхронизируются движком из `current`, а в
библиотеке нет файлов движка.

### Этап 8. Документация

1. **README движка на GitHub:** что это, установка сервера и клиентов,
   обновления, откат.
2. **Шаблон README библиотеки** с командами подключения.
3. **Обновить `AGENTS.md`**, системные скиллы (`maintain-skill-catalogs`,
   `add-shared-skill`, `check-skill-updates`), `server/README.md` и
   `tests/README.md` под разделение.

## Статус этапов 3–8 (2026-11-05)

Всё ниже сделано в локальном репо `Skillarium` и покрыто тестами; на GitHub
ещё не опубликовано, поэтому выпусков и CI на Linux пока не было.

- **Этап 3.** `scripts/skillarium.sh`/`.ps1`: `install`, `self-update
  [--channel]`, `rollback` (с пропуском версии), `status`, `enable-updates`;
  они же — загрузочные скрипты выпуска (`server`/`client` ставят движок и
  запускают установку роли). Рядом с версией хранится её `release.json`.
  Команда установки — не `install.sh engine`, а `skillarium install`: старый
  `install.sh` остаётся клиентом. Тесты: `test_engine_install.py`.
- **Этап 4.** `skillarium server` → `server/setup.sh` (зависимости, linger) и
  `server/setup.py`. Сервер закрепляет `policy_engine` своим PR
  (`manage.py pin-policy`, правило в `policy.py`: только сервер и только
  вперёд). Тесты: `test_server_setup.py`, `test_policy.py`, `test_server.py`.
- **Этап 5.** `skillarium client` → `scripts/setup-client.*`. Тесты:
  `test_client_setup.py`.
- **Этап 6.** electron-builder (NSIS per-user, AppImage, движок в
  `resources/engine`), electron-updater (каналы через `allowPrerelease`),
  раскладка движка в `versions/<v>` + `current` при запуске, экран первого
  запуска, баннер обновления. Выпуск собирает установщики после тестов и
  кладёт их в `latest.json` (`app.*`). Распакованная сборка Windows проверена
  вручную: движок раскладывается, `current` — junction. Подписи нет.
- **Этап 7.** Мост `scripts/bridge.*` в синхронизации старой раскладки,
  `release/migrate_library.py`, порядок шагов — `docs/migration.md`. В
  `agent-skills` — ветка `skillarium/bridge` с движком Skillarium и мостом
  (не слита, не отправлена). Отдельная команда `manage.py migrate` по-прежнему
  не нужна, пока нет второй версии формата.
- **Этап 8.** README (установка, обновления, движок и библиотека),
  `server/README.md`, `tests/README.md`, `AGENTS.md`, системные скиллы.

Осталось за пользователем: опубликовать `Seekeer/Skillarium` и выпустить
`v0.1.0`, затем шаги `docs/migration.md` (слить мост, поставить сервер на i3,
убрать движок из библиотеки, поставить приложение).

## Проверка

Сохраняются правила `AGENTS.md`:

- временные Git-каталоги, bare remote, `fake_hosting.py`, временные HOME;
- Windows — только нативно.

Добавляются:

- локальный сервер выпусков для `self-update` и клиентской установки;
- расширенная имитация Gitea для установки сервера;
- e2e приложения на первый запуск;
- тест мостового выпуска: старая установка → движок в `current` без потери
  локальных правок.

## Решения по открытым вопросам (2026-11-05)

1. **Репо на GitHub** — пока не выбрано. Адрес задаётся одной константой
   (`SKILLARIUM_RELEASES`, плейсхолдер `OWNER/skillarium`) и подставляется
   позже одной правкой.
2. **Доступ клиентов по умолчанию** — служебный бот. Установщик сервера
   создаёт пользователя-бота и его токен. Клиентская установка запрашивает
   этот токен. Отдельные учётные записи остаются опцией.
3. **Подпись Windows-установщика** — пока без подписи.
4. **Клон библиотеки на клиенте** — `~/Skillarium/library`
   (`%USERPROFILE%\Skillarium\library`).
5. **`policy.py` в проверке PR** — скачивается с GitHub по закреплённой
   версии, сверяется sha512. Раннер должен видеть GitHub.
