# Сервер библиотеки скиллов

Серверная роль — не отдельный репозиторий, а назначаемая машина. Она
обслуживает внешние источники, реестр и базы `upstream/<name>/`. Назначение
хранится в `agent-skills.json` (`server.machine`), первоначально `i3`.
Серверу нужны Python 3.9+, Git (лучше 2.38+ для слияния без рабочей копии),
Bash, flock и пользовательский systemd.

```bash
python3 server/manage.py status
python3 server/manage.py check
python3 server/manage.py maintain --apply-auto
```

`status` показывает машину, назначенный сервер, отчёт последней проверки,
ожидающие предложения и состояние клиентской публикации. `check` (и
`maintain --dry-run`) — проверка без публикации; работает на любой машине.
`maintain` запускается только на назначенной машине: имя берётся из
`git config agent-skills.machine` и сравнивается с `server.machine` в
актуальной `origin/main`. Без доступа к хостингу публикация остаётся
ожидающей. `--catalog agent-skills` и `--publish` приняты для совместимости.

## Как работает обслуживание

Сервер берёт блокировку той же рабочей копии, что и клиент, получает
`origin/main` и работает во временной worktree и в объектах Git. Активная
установка сервера не меняется: принятые результаты приходят обычной
синхронизацией клиента.

1. Учёт: доработки, опубликованные клиентами, записываются в `customization`,
   новые корректные папки регистрируются как `source.kind=local`, недостающие
   папки заполняются закреплёнными версиями, старые
   `customizations/<name>/<hash>/` переносятся в `skills/<name>/`.
2. Для каждого внешнего скилла сравниваются база (`upstream/<name>/` —
   закреплённая внешняя версия из собственной истории), общая версия
   (`skills/<name>/`) и найденная входящая версия. Учитываются байты, наличие
   файлов и права исполнения. Совместимые изменения обеих сторон объединяются
   трёхсторонним слиянием Git вне установки.
3. Чистый результат при политике `auto` попадает в серверный PR
   `agent-skills/server/<машина>/<ключ>` с автослиянием. Политика `confirm`
   и любой конфликт дают предложение `agent-skills/update/<name>/<ключ>`
   (PR без автослияния). Для конфликта результатом является наша версия с
   новой базой, а копия с маркерами лежит в `agent-skills/materials/<name>/<ключ>`.
4. Повторная проверка неизменённого предложения не создаёт новых PR; при новой
   входящей версии или изменении общей папки прежнее предложение закрывается.

Отчёт пишется в `.git/skill-updates.json`; код 1 означает конфликт, ошибку
или недоступный источник. Недоступный или удалённый источник не удаляет
установленный скилл.

## Команды сервера

```bash
python3 server/manage.py register example --git-url https://example.org/owner/repo.git --path skills/example --ref refs/heads/main --policy auto
python3 server/manage.py register example --url https://example.org/SKILL.md --policy confirm
python3 server/manage.py set-policy example confirm
python3 server/manage.py approve example --revision <incoming-revision> --commit <reviewed-head>
python3 server/manage.py resolve example --revision <incoming-revision> --commit <reviewed-head> --shared-hash <sha256> --strategy keep-shared|take-upstream
python3 server/manage.py resolve example --shared-hash <sha256> --strategy detach
python3 server/manage.py import-local /path/to/my-skill [--dry-run|--no-publish]
```

`register` проверяет структуру, Windows-пути и точный SHA256 и публикует
папку, базу и запись через серверный PR. `--auto-update yes|no` по-прежнему
означает `--policy auto|confirm`. `approve`/`resolve` принимают только
актуальное предложение с указанной revision и общей версией; их можно
выполнить на любой машине с Python. Клиентские аналоги без Python описаны в
корневом README. `detach` превращает внешний скилл в собственный (только сервер).
`import-local` копирует папку в `skills/<name>/` и запускает синхронизацию
клиента; запись в реестр сервер добавит сам.

## Правило PR и настройки хостинга

`server/policy.py` — обязательная проверка PR (`.gitea/workflows/policy.yml`,
событие `pull_request_target`, поэтому правило и назначение берутся из
основной ветки, а не из предложения):

- PR должен содержать актуальную основную ветку;
- изменения `skills/<name>/` принимаются от любого автора после технических
  проверок (frontmatter, Windows-пути, ссылки, 32 MiB);
- каждое изменённое значение записи `sources.json` и база `upstream/<name>/`
  должны совпадать с результатом коммита, автор которого — служебное имя
  назначенного сервера `agent-skills/<server.machine>`; смешанный PR
  проверяется по каждому значению, исторические коммиты не проверяются;
- удаление скилла целиком требует того же служебного автора;
- изменение `agent-skills.json` допустимо только отдельным PR с коммитом
  `Agent-Skills-Admin: assign-server`.

На Gitea для `main`: запрет прямого push (`enable_push: false`), обязательная
проверка `Library policy / policy (pull_request_target)`,
`block_on_outdated_branch: true`, стиль слияния `merge` (авторство коммитов
сохраняется). Токены клиентов — с правом записи в репозиторий.

Проверено на Gitea 1.27.3 (временная защищённая ветка, 2026-11-02): прямой
push отклоняется, слияние без успешной обязательной проверки запрещено,
`pull_request_target` создаёт статус `Library policy / policy (pull_request_target)`,
повторный запрос автослияния отвечает 409 «already scheduled» (клиенты снимают
и ставят его заново). Ограничение: при планировании автослияния Gitea не
сверяет `head_commit_id` (принимает любое значение), поэтому точность
одобрения обеспечивают проверки клиента перед запросом и то, что сервер не
дописывает в ветку существующего предложения. Фактическое слияние после
проверки не наблюдалось: runner Actions в это время не брал задачи; повтор —
`python tests/gitea_rules.py --clone-url <url> --from origin/<ветка>`. Проверка
авторства по имени — согласованный компромисс доверенной сети: она
останавливает случайно запущенный второй сервис, но не защищает от намеренной
подстановки имени.

## Передача серверной роли

```bash
python3 server/manage.py assign-server <machine>
```

Явная административная операция на любой машине, в том числе при недоступном
прежнем сервере: отдельный PR меняет `agent-skills.json`, открытые серверные PR
и предложения прежней машины закрываются. Даже восстановленные, они больше не
проходят проверку: она использует назначение из актуальной основной ветки.
Затем на новой машине: `bash server/install.sh --install <machine>`; на
прежней — `bash server/install.sh --uninstall`. Автоматического выбора
сервера нет.

## Расписание и переход со старого updater

```bash
bash server/install.sh --install i3
systemctl --user start agent-skills-server.service
journalctl --user -u agent-skills-server.service -n 30
```

Установщик записывает имя машины в локальную конфигурацию копии, включает
ежедневный `agent-skills-server.timer` (`server/run.sh` → `maintain
--apply-auto`) и отключает управляемый таймер прежнего agent-skills-updater,
чтобы старое и новое обслуживание не конкурировали. Чужие unit-файлы и сам
каталог прежнего updater с его локальными изменениями не трогаются; после
проверенного перехода прежний репозиторий можно архивировать. Код сервера
обновляется обычной клиентской синхронизацией этой копии.

Порядок перехода: слить объединённую ветку в `main` (вручную, проверка ещё не
действует), включить защиту `main` с проверкой, на i3 выполнить
`bash install.sh --sync-only` и `bash server/install.sh --install i3`,
затем `maintain --apply-auto` и проверить, что клиенты получают результат.
Клиенты переходят сами: после получения нового кода их неопубликованные
автоматические коммиты уходят через PR, ссылки и расписания сохраняются.

## Объединение историй

История agent-skills-updater присоединена командой

```bash
python3 server/manage.py absorb-updater --updater ../agent-skills-updater --revision <commit>
```

Она требует чистые копии (грязные сохраняются и перечисляются), шаблоны
`client/` ставит на место корневых файлов только если те совпадают с
эталоном или с манифестом владения, прочие коллизии путей останавливают
операцию. Результат — один merge-коммит с обоими родителями; ветка
обновляется только fast-forward, поэтому прерванный запуск безопасно
повторить, а повтор после успеха ничего не меняет.

## Клиентские файлы

`install.sh`, `install.ps1`, `scripts/*`, корневые README и `.gitattributes`
— единственный эталон клиента; `.agent-skills-client.json` хранит их хеши
(LF/CRLF не учитываются). После правки клиента выполните
`python3 server/manage.py client-manifest --write` в том же изменении; CI
проверяет актуальность манифеста. Такие изменения публикуются обычным PR
разработчика и не попадают в автоматические клиентские коммиты.
